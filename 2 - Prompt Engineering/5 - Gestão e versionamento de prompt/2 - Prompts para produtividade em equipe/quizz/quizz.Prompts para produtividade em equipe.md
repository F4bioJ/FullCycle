# Quizz — Prompts para produtividade em equipe

**Capítulo:** 5 - Gestão e versionamento de prompt · **Aula:** 2
**Base:** material da aula

---

## 1. Um tech lead escreve sozinho o prompt de revisão de código que o time vai usar e avisa que essa é a versão definitiva. Pelo que a aula defende, qual é o principal problema dessa abordagem?
- A) Prompts de produtividade são pessoais, então cada dev deveria manter a própria versão na máquina.
- B) Ela corta a iteração: o prompt melhora quando vários devs o testam e propõem ajustes ao longo do tempo.
- C) Antes de adotar o prompt, o time precisaria definir métricas objetivas que provassem a qualidade dele.
- D) O problema é de registro: salvar o prompt no Git já resolveria, sem precisar de testes de outros devs.

## 2. Segundo a aula, por que prompts de produtividade são mais difíceis de avaliar de forma objetiva do que prompts usados dentro de outros sistemas?
- A) Porque as técnicas de evaluation foram feitas para prompts de aplicação e não servem para os de desenvolvimento.
- B) Porque o mesmo prompt varia conforme o modelo, o que impede comparar duas versões do prompt entre si.
- C) Porque o trabalho avança em várias iterações, quase nunca em one-shot, e o efeito do prompt se mistura ao processo.
- D) Porque o code review de prompts depende da opinião de quem revisa, o que impede o uso de métricas na avaliação.

## 3. Sobre o fluxo sugerido para prompts de produtividade compartilhados pela equipe, qual afirmação está INCORRETA?
- A) A versão aprovada como principal passa a ser revisada quando o time troca de modelo, e não por novos testes.
- B) Uma mudança no prompt do time entra por pull request, para que outros devs a testem e revisem antes.
- C) Um prompt que funciona bem com um modelo pode precisar de adaptação quando o time passa a usar outro.
- D) O fluxo é uma sugestão compilada de conversas com outros devs, e cada time pode adaptá-lo ao seu jeito.
